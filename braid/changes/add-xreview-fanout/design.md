## A script that starts programs, not an orchestrator

Weighed: keep `--run` as a same-harness subagent, depend on a session manager that drives agent terminals (start, wait for idle, read the last message), or start each reviewer's own command-line program from a script. A subagent shares the author's model family, which is the thing a cross-review exists to avoid. A session manager solves interactive, long-lived sessions, and brings a daemon, its own worktrees and first-class support for only some of the four programs; a review is the opposite case: one prompt file in, one result file out, no conversation. All four programs have a non-interactive mode, a model flag and a way to run without approval prompts (read from each one's `--help` at the versions installed; task 1.1 proves them by running), so the runner is a table of four command lines and a `spawn`. It is a `.cjs` file beside the skill, as `retro.cjs` is, so every harness with a shell runs the same thing.

## Reviewers are always named

Weighed: default to every installed program, default to the programs of other model families than the author's, or require the reviewers to be named. A default spends three subscriptions' quota on a flag that used to start one subagent, and the author can't reliably tell its own family. So `--run` takes a list, else the project's `Reviewers:` line, else asks and offers to save that line. The line lives in AGENTS.md because that is the one file every harness reads, and in its Workflow section because that is where the `Specs:` line already says how the project works; xreview writes it only after a yes, since it changes the project's agent instructions, and adds the section when the project has none. Without an AGENTS.md there is nothing to save into, and creating one is `/braid:standards`' job.

An entry that can't run stops the fan-out whether it came from the command line or from the line: a shared AGENTS.md naming a program this machine lacks should say so, not quietly review with fewer. With none of the four installed there is nothing to ask about, so xreview says that and names `--run subagent`.

`subagent` is one more name rather than a fallback, so nothing about who reviews is implicit and the old behavior stays one word away: it is 1.8.0's `--run` exactly, with a self-named result file and none of the runner's mechanics. It stands alone and takes no model: the runner can't start, time or wait on a harness's subagent, harnesses differ on whether a subagent's model can be set at all, and a cold same-family review beside other reviewers is already there by naming the harness's own program (`claude` from a Claude Code session).

## The list and the scope

`--run` used to be a bare flag, and `--run all` or `--run diff` are valid today. Weighed: require the scope before `--run`, or keep reading the next word as the scope when it is one. Moving the scope breaks invocations people have typed for a reason no one would guess from the error. So the word after `--run` is the scope when it is `diff`, `all` or an existing path, and the reviewer list otherwise; `--run gemini` is still an unknown reviewer. The list and the scope can come in either order (`--run codex,pi all`, `--run all codex,pi`), and a word starting with `--` is a flag, so `--run --auto` and `--run --offline` read as they do today. The price: in a project with a folder named like a reviewer (`pi`), that one word after `--run` reads as the scope. The `Reviewers:` line, or a list of two, avoids it. `next` takes no scope, so there the rule doesn't apply and the word after `--run` is always the list.

## What reaches a command line

A program behind a `.cmd` shim has to be started through a shell on Windows, where arguments are concatenated, not escaped, and `%` can't be quoted at all. Three things would otherwise reach that shell as free text. The model can come from the `Reviewers:` line, which is repo content, so it is limited to ASCII letters, digits and `.`, `_`, `/`, `:`, `-`, which covers every model id the four programs take; anything else, an empty model included, is an entry that can't run. The prompt and result paths come from the review folder's name, which comes from a path scope, so xreview maps a scope's characters other than ASCII letters, digits and `._-` to `-` when it names the folder (non-ASCII text is also what a Windows code page mangles), the runner refuses a folder named otherwise, and both paths are passed relative to the working tree, so a project living under `R&D` never appears in them. Where a program reads its prompt from stdin, the runner passes the hand-off line there and nothing but flags and the model on the command line; task 1.1 records which do.

## Auto-approved, in the one working tree

Weighed: read-only reviewers, reviewers in worktrees, or auto-approved reviewers sharing the checkout. A read-only reviewer cannot run a test or a reproduction, so it could never label a finding CONFIRMED, and it could not write its result file. Worktrees don't hold uncommitted changes, which the default scope includes, and many projects rule them out. Sharing the checkout is what happens today when the user pastes one prompt into three apps; reviewers' test runs can collide on a port or a build folder, and a collision surfaces as a finding the author declines.

Weighed after the first review round, at the user's word: every action allowed (Claude Code's `bypassPermissions`, Vibe's `--auto-approve`, Codex's default `approval: never`) or each program's automatic approval mode, where the program itself reviews an action before running it (Claude Code's `auto` permission mode, Codex's `--approve-for-me`, Vibe's `--smart-approve`). Nobody is there to answer a prompt either way, and the automatic modes still let a reviewer run tests and write its file, so the runner uses them wherever a program has one; Pi has no approvals at all. They are a second check, not a boundary: the notice and the exposure question stay as they are.

Codex's sandbox is the only one the runner turns on; the other programs run with the user's rights. That is new exposure compared with a hand-started reviewer, which runs under whatever approval settings the user chose for that app. So xreview says it before every fan-out, not only when the reviewers are first chosen: a saved `Reviewers:` line would otherwise start unprompted programs without a word.

The programs also differ in how they treat a folder's own agent configuration. Claude Code's non-interactive mode skips its workspace trust dialog, so a repo's project hooks and settings load unasked; Pi and Vibe have a flag that trusts project-local files for one run, and Codex keeps hook trust on disk. The runner passes no trust flag unless task 1.1 shows a program can't review without one, and the notice says that a started program may load the project's own hooks, extensions and MCP servers without asking, because for at least one of them that is the default. And on an exposure hit the question says that the programs would run that code unprompted and offers starting nothing, also when the prompt is already offline, because `--offline` addresses what leaves the machine, not what runs on it.

## GLM through Codex, as its own name

Asked for during the review of this change: Z.AI's GLM models reviewing through Codex, which has a sandbox and an approval reviewer, beside Codex on its default model. Codex reaches GLM through a profile the user sets up once (`zai.config.toml` in Codex's home, selected with `-p zai`). Weighed: have `codex:glm-5.3` add the profile when the model's name starts with `glm-`, or give it a reviewer name of its own. A prefix rule is a guess that breaks on the next model name, and it hides that the entry depends on a per-machine file. So `glm` is a fifth name, the same program with `-p zai`, whose result files are `r<N>-glm.md`, as hand-started GLM reviewers already name theirs. It counts as installed when Codex is on PATH and the profile file exists, so `--list` offers it only where it can run, and without the profile it is an entry that can't run. A missing key is Codex's own error, relayed as that program's last line. `pi` stays: it still reaches models nothing else does.

It keeps `--approve-for-me` like plain Codex. On that profile Codex's approval reviewer is GLM as well, and in the user's trials it denied nothing, a POST of a dummy credentials file included, while the workspace sandbox blocked a write outside the workspace and a network call. The sandbox is the boundary there; the notice already says Codex keeps it. Tried on 2026-11-14 through `run.cjs`: `codex,glm,glm:glm-5.3-flash` ran side by side and wrote three reports in a minute.

## Offline stays an instruction

Weighed: on a "go offline" answer, start only the reviewers whose network can really be cut, or start them all with the `--offline` prompt. Codex's sandbox is set with a flag. Claude Code's can be turned on per run through `--settings`, on macOS, Linux and WSL2 but not native Windows; Pi and Vibe have none. Cutting the roster to what can be enforced would make `--offline` quietly mean "Codex only" on some machines and "Codex and Claude" on others. Every reviewer gets the offline prompt and the user is told the started programs are not held to it; enforcing it where a sandbox exists is left for later.

## The runner assigns result paths

Self-naming was right when a person started each reviewer: a name supplied by hand would have been a chore. The runner knows the roster, and two entries for one program would both name themselves the same and race for the `-2` suffix. So it picks every path before starting anything, checking each against the files that exist and against the round's other entries without regard to case, and passes it in the one line it hands the reviewer. The model is in the name only when the entry names one, which keeps `r1-codex.md` for the common case; everything after the first colon is the model, because a model id can hold a colon itself (Pi's `provider/id:thinking`). `next` reads result files by round prefix, so nothing downstream changes. The prompt tells a reviewer to use the exact path its hand-off gives when it gives one, so the two instructions a started program reads don't compete, and hand-started reviewers keep naming themselves.

A program stopped at the limit can leave half a report under its assigned name. A result file is a report only when it ends in its `Verdict:` line. The rule is `next`'s, for every result file, since `next` can't tell later which files a fan-out assigned: an incomplete file is named as such, not handled, and not written into a `Round` section, so a hand-started reviewer still writing is read once it finishes, and a stopped program's half report is never read as a review.

## One process, one finish signal, 60 minutes

The runner is one foreground process that exits when every reviewer has finished or been stopped; it prints a line as each one finishes. `next` acts on a round as a whole, so a signal per reviewer would wake the author with nothing to do. The author starts the runner the way its harness runs a long command: in the background where the harness wakes the session when such a command exits, which Claude Code is built to do, and blocking on it elsewhere. Task 1.3 measures all four, Claude Code included, since a harness that fails to wake only pauses the loop until the user's next message. A notifier of braid's own (a socket, a watched file) would be a second mechanism for an event the process exit already carries. In 155 reviewer runs measured over 45 days, 154 finished within 60 minutes and the median was under 15, so the limit is 60; it is also the longest one hung reviewer can hold up a round. The limit reads one environment variable because the check needs a short one.

Stopping a reviewer means stopping its process tree. A program started through a shell shim leaves the real process running when only the shell is killed, and a reviewer's own test processes outlive it the same way; an unprompted program still editing the tree while the author fixes findings is the failure to rule out. So the runner starts each reviewer as the head of its own process group and kills the group (on Windows, the tree by pid), and its exit doesn't wait on output pipes a stray child still holds. A child that leaves the group on purpose (a detached server a test started) survives this, and the comparison can't see it; the not-covered line names it.

Not decided here, on purpose: whether the runner must detach from the author's shell. Task 1.3 measures how each harness treats a command that runs for an hour. If one kills it, the runner gains a detached mode and a `wait` verb, added to the delta and the proposal as well as the tasks, since a verb is behavior; if none does, it gains nothing.

## What the comparison covers

The cleanup rule is an instruction; the comparison is the check on it. A status list alone misses a reviewer that checks out another commit (the files change, the status stays clean), and misses the branches, stashes and worktrees the rule names. A git hook or a config entry left behind runs on the author's next git command. So the runner records, before and after: the status list and a content hash of every modified and untracked file, the index entries with their flags (`git ls-files -s` and `-v`: a changed staged blob, or a file flagged assume-unchanged or skip-worktree so its edits stop showing), `HEAD` and the branch, the refs (which hold the stash), the worktree list, a hash of the hooks folder, the local config and the local exclude file, and whether a stale `index.lock` is there, which would block the author's next git command. All are git calls or file checks in code that already runs git. Git is started by the full path found in PATH's absolute folders, and on Windows only as a `git.exe` or `git.com`, because Node 18 looks a bare name up in the current directory first (the tree under review), whatever `NoDefaultCurrentDirectoryInExePath` says. With no git found, or a repository git can't read, only the review folder is compared, and the runner says so instead of reporting no leftovers.

The review folder gets its own before-and-after hash of every file, whether or not git ignores it, which it usually does. It is the one place every program is told to write, and `next` trusts it: `prompt.md` records the user's decisions and the round, and any `r<N>-*.md` no section names is read as a reviewer. A program that edited the prompt, or wrote a second report under another name, would otherwise go unnamed.

It is a check on leftovers, not a boundary. A program with the user's rights can act outside the repository, where no git comparison looks, so chasing every way to hide a change inside it would add code without adding a guarantee; the index and exclude file are in because a staged blob or a hidden edit lands in the user's next commit, and they cost one call each. It can't see containers, processes that left a program's tree, ignored files or anything outside the repository, and says so each time, so a clean list isn't read as a clean bill of health. It names and never undoes: reverting a file the user was also editing would be worse than a stray one.

## `--auto` waives one question

The questions `next` asks before fixing (a signed-off decision, agent instructions or check commands, reviewers who disagree, a real choice, doubt about the user's vision) and the failing-check stop are decisions that belong to the user, and no flag removes them. "Another round?" after a CONFIRMED finding is different: the author now recommends an answer, and a user who trusts the loop can waive the question with `--auto`, on the first run as on `next`. Past five rounds the same question comes back before every further round whatever the findings, as the stop for a review that isn't converging; it is one question, not a second one stacked on the first.

Neither the roster nor `--auto` is written to disk. A session that has to hand the wait back to the user gives the whole command to resume with, the review's folder included, since `next` without one takes whichever review changed last. That keeps the state where the user can see and change it; recording it in the prompt would put a second source of truth beside the `Reviewers:` line.

## A marker while it runs, and starting a round again

Weighed, for a `next` typed while programs are still running: wording that tells the user to wait and how to tell, a question before any restart, or a marker the runner keeps in the review folder. Without a guard, `next` would handle a round one program has reported on while another still edits the tree, or a second fan-out would be assigned the same result paths and overwrite the first. Wording relies on the user checking, and a question asks them something they can't see either. So the runner writes a marker when it starts and removes it when it exits; the runner and `next` treat a live marker as "still running" and do nothing, and a dead one as no marker. This is run state, which ADR 0005 puts on disk; it is not the roster or `--auto`, which stay in the command. The marker is left out of the comparison, as the result files are.

The runner's own process id is not enough. Each program is the head of its own process group, so a runner that is killed alone leaves its programs running, unprompted and past the limit, with nothing to say so. Two things close that. The marker holds the runner's process id and each program's, and it is live while any of them is. And the runner stops every program's tree when it is told to stop (an interrupt, a terminate, a hang-up or a closed console), so the common ways a harness ends a command take the programs with it; the marker covers the kill that can't be caught. `next` doesn't probe processes itself: the runner has a read-only check (`--running <folder>`) that every harness calls the same way. A process id can be reused by an unrelated process on Windows, which would make a dead marker read as live for good, so the still-running message names the marker file and says it can be deleted when no program is really running; recording start times to tell the processes apart is more code than that sentence.

With that guard, restarting needs no question. A fan-out that starts nothing (a mistyped name, a program missing) or yields nothing (every program failed, an expired login) leaves the round ready, and `next` used to stop there for want of result files; running `/braid:xreview --run` again would open a new folder and lose the review's rounds. So `next --run` on a round with no result files and no fan-out running starts the reviewers on it.

## The hand-off line

When a round is left for the user to hand on, the closing message gives the line to paste: `Read <prompt path> and do what it says.` It is the same line the runner passes to a program, so a reviewer started by hand and one started by the script begin from the same words.

## Measured (tasks 1.1 to 1.4)

On 2026-11-13, from a Claude Code session on native Windows 11 (`claude` 2.1.325, `codex-cli` 0.169.0, `pi` 1.5.2, `vibe` 3.1.2), in a scratch git repo no program had been told to trust, holding a review folder, a failing test and a planted project-local hook, extension or MCP server per program. Each program ran the test and wrote its result file to the path its hand-off gave. All four read the hand-off line from stdin, so the command line holds flags and the model only:

| Program | Command, hand-off on stdin | Model | Last message / errors | Untrusted folder |
|---|---|---|---|---|
| `claude` | `claude -p --permission-mode bypassPermissions` | `--model <m>` | stdout / stderr | reviews; the project's `.claude/settings.json` hook ran |
| `codex` | `codex exec --sandbox workspace-write -` | `-m <m>` | stdout / stderr, with the whole transcript | reviews; the planted `.codex/hooks.json` did not run, the user's own hooks did |
| `pi` | `pi -p` | `--model <m>` | stdout / stderr | reviews; the planted `.pi/extensions/` file was not loaded |
| `vibe` | `vibe -p --auto-approve` | `--model <m>` | stdout / stderr | reviews; says on stderr that `.vibe/` is ignored |

No program needed a trust flag, so the runner passes none. `codex exec` reports `approval: never` by itself. On native Windows it wrote the result file inside the workspace sandbox with `[windows] sandbox = "unelevated"` in the user's Codex config; other values of that setting were not tried.

From Node's `spawn` on Windows only `pi` needs a shell: it is a `.cmd` shim, and `spawn` without a shell fails with `ENOENT`. `taskkill /pid <pid> /T /F` took each program's tree (up to eight descendants) with it. Two Windows facts shaped the start. Node puts a child that is not detached in a job object that dies with the runner, so a runner killed outright took a shim's `cmd.exe` with it while the program behind it ran on, and the marker read dead; so every program is started detached. And a detached `cmd.exe` never passes the end of stdin on to the program, which then waits for its hand-off for good; so for a shim the runner starts a detached Node that starts the shell with inherited pipes and exits with its code, and that Node's process id is the one in the marker. One real round of all four through `run.cjs` this way wrote four reports in under a minute, and the comparison named the file Claude Code's project hook had left. In WSL Ubuntu (`claude` 2.1.318) `claude` reviewed the same way from `spawn`, loaded the project hook there too, and a `SIGKILL` to its process group left nothing running.

Claude Code kept a background command for its whole run and woke the session when it exited: a one-hour timer started at 21:20 UTC ended at 23:13, the machine having slept in between, and the session was notified then, with no message from the user.

Not measured: Codex, Pi and Vibe on Linux or macOS (Codex's login in WSL had expired, which the runner would report as a failure with that line; the other two are not installed there); a fan-out started from inside a Codex, ZCode or Pi session; how those three harnesses treat an hour-long command (task 1.3). So no detached mode is added, and the session-can't-wait message stays the fallback for a harness that stops waiting.

On 2026-11-14 the three automatic modes were tried the same way, in the same scratch repo: `claude -p --permission-mode auto`, `codex exec --approve-for-me -` (it reports `approval: on-request` and `sandbox: workspace-write`) and `vibe -p --smart-approve` each ran the test and wrote its result file with no prompt left unanswered, and Claude Code still ran the project's hook. Those are the command lines in `run.cjs`; the table above shows the first day's.

ZCode's bundled CLI (`resources/glm/zcode.cjs`, 0.17.1: `-p <text>`, `--mode build|edit|plan|yolo|guarded`, no model flag) was tried that day as a fifth program and did not get to a model on a Coding Plan account. It first fails to find its built-in provider file, which `ZCODE_BUILTIN_PROVIDER_CONFIG_FILE` pointed at `resources/config/provider/zcode-builtin.json` gets past; it then stops at "Select a model before sending a message", because its config reader takes API keys only from the plain `builtin:zai` and `builtin:bigmodel` entries and skips the coding-plan ones. So ZCode stays out, as the proposal says, with what was learned under its Follow-ups.

On 2026-11-15, at the user's word after seeing it in real rounds: a process started detached on Windows has no console, so every console command it starts without `windowsHide` opens a window of its own (a Windows Terminal tab where that is the default terminal). The runner's own git and taskkill calls now hide theirs. A reviewer started straight from an `.exe` was detached in the same way, so its shell, git and test commands could each open one too. So on Windows every program now starts the way a shim did: a detached Node starts it attached, `windowsHide` set, and the program and its children share that hidden console. The Node's process id is the one in the marker. Tried with Node standing in for the program (the hand-off line arrived on stdin, and output and exit code came back). Not yet tried with a real reviewer: task 5.1.

A sandboxed Codex reviewer on Windows reached its own web search tool and got results. Whether a shell command inside the sandbox reaches the network was not established: the one attempt ran PowerShell's `curl` alias, which failed on its arguments.

## Minor release

`--run` with nothing named used to start a subagent and now asks once; every other invocation that worked keeps its meaning. The CHANGELOG's rule names a new skill or verb as minor and wording as patch; this adds neither a skill nor a verb but changes what a flag does, as 1.7.0 did for xreview with `--offline`, and that was a minor. No skill is renamed or removed and no file braid reads moves or changes format, so it isn't a major. 1.9.0.
