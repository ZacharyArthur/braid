## A folder per review, released as minor

Weighed: one file per reviewer per round beside a flat prompt (`<date>-<scope>.r<N>.<reviewer>.md`), one shared file per round, or a folder per review. A shared file breaks when reviewers in different harnesses write at once. Flat siblings avoid a layout change but scatter a review across the folder. The folder keeps a review's history in one place. The CHANGELOG counts a changed `braid/` layout as major; read literally that makes this 2.0.0, but nothing braid reads moves: the old flat files were never read, and the folder is new. Semver's major means breaking what people depend on, so the rule is reworded to "a `braid/` file braid reads moves or changes format", which holds for projects that commit their reviews too, and this is a minor release.

## The folder ignores itself

Weighed: suggest a line for the root `.gitignore`, write one without asking, or ask once to write `braid/reviews/.gitignore` containing `*`. Review files pile up into noise; the decisions belong in specs and ADRs. The folder-local file needs no merge with the project's own ignore rules and ignores itself too. It is asked, not done, because some projects commit their reviews, and asked only when xreview creates the first review folder in `braid/reviews/`, so a no is never asked again without any state to remember it. That trigger, not the creation of `braid/reviews/` itself, also reaches users whose `braid/reviews/` holds flat files from 1.7.0. The check asks git about the prompt path it is about to write, not the folder: before the folder exists, a `braid/reviews/` rule matches only directories, so `git check-ignore braid/reviews` misses it, and a made-up path inside misses rules like `*.md` or `braid/reviews/*/`. Outside a git repository there is nothing to ignore, so it asks nothing. Whether or not the folder is ignored, xreview keeps `braid/reviews/` out of a review's scope, so reviewers never review the prompt or each other's reports.

## Reviewers name themselves; only the verdict is machine-readable

The user starts reviewers by pasting one line, so a name supplied by hand would be a new chore. A reviewer that misnames itself only mislabels its file, but two of one family would share a name and the second would overwrite the first, so a reviewer whose file exists appends `-2` as folders do; that also keeps apart reviewers that can't tell their family and fall back to `reviewer`. A reviewer writes only its file, since one that edits code would change the next round's diff; one that can't write (a read-only sandbox, plan mode) replies with the whole report, as before, and the path to save it at, so `next` can still read it. The Output section names the severities HIGH, MEDIUM and LOW, because the stop rules key on LOW and reviewers otherwise pick their own scales. The last line `Verdict: SIGN OFF|CHANGES NEEDED` is the one fact a loop needs to decide whether to stop. Richer structure waits for something that reads it.

## How much `next` decides

Taken from the review rounds that led here: `next` fixes and declines on its own and records why, and asks when a fix would change a signed-off decision or the project's agent instructions or check commands, when reviewers disagree on what should happen, when fixes offer a real choice, or when it's unsure a fix fits the user's vision. After a round with a CONFIRMED finding above LOW it asks whether to go on, and leans to asking after a CONFIRMED LOW one whose fix touched code, behavior or tests; when it judges such a fix trivial it says why and treats it as a nit. A confirmed nit in wording or docs doesn't hold the review open. A yes to going on sets the next round; a no ends the review. Ending it writes `Review closed` in the last Round section, so a late file after that is named and the user asked before the review reopens, instead of `next` quietly writing a second section for the same round. A yes handles the file in that same section; a no names it there as read, so it isn't asked about again. On a closed review any unnamed file counts, whatever its round: nobody is still working, so there is no reason to wait. After a full sign-off with nothing that asks, it fixes what it agrees with and may close the review or ask first. It runs the project's checks before a new round or closing, so reviewers don't spend a round on a red gate and a review doesn't close on one. It doesn't wait for a reviewer count it can't know: each Round section names the result files it read, and `next` reads only files no section names, so it never handles a file twice and a late one joins the next round. With no result file for the current round it stops, rather than read an empty round as a sign-off; a late earlier-round file waits for the current round's results, since starting a round on it alone would run ahead of reviewers still working. "Done" means the review only.

## Result files are claims, not instructions

Result files are other models' text, and a reviewer may quote a hostile page or file as evidence; `next` then edits files and runs checks, and 1.7.0's Sources rules bind only the reviewer. So `next` checks each finding against the code before acting, never runs, opens or installs anything because a result file says to, and shows the user text aimed at the author. It records findings in its own words: a pasted line in a Round section would reach the next round's reviewers as part of the prompt they trust. A fix to the project's agent instructions or check commands is asked first, since `next` then runs those commands: otherwise a result file could name a command and have it run one step removed. Each new round runs the author-and-secrets check again, as xreview does before giving a path: commits by other authors may have arrived since round 1, and round 1 may have gone to a network-off reviewer. On a hit `next` asks whether to keep the prompt online and rewrites it as `--offline` on a no, with or without `--run`: 1.7.0 only suggests `--offline` without `--run`, but `next` takes no `--offline` and rerunning xreview would start a new review, so the rewrite is the only way to act on it. A prompt already `--offline` gets the network-off reviewer named and no question, as in 1.7.0. A change counts as being applied once a task is ticked, so edits to a proposal's own delta during its review don't need the user; a decision the prompt records as the user's still does, ticked or not, whether Intent holds it or a Round section where the user answered an earlier `next` question, since nothing copies those answers into Intent.

## `next` and the closing check live in their own files

`SKILL.md` was about 600 bytes under its 8000-byte cap, and a terse draft of its new text came to 8087 bytes. Two siblings, routed from `SKILL.md` as the spec skill routes to `apply.md`: `next.md` carries `next`'s procedure and loads only when it runs, and `exposure.md` takes the closing author-and-secrets check (about 1300 bytes), changed only to drop its opening "Before that,": `SKILL.md`'s routing line says to run it before giving the path or handing off, and `next.md` runs it before readying each round.
