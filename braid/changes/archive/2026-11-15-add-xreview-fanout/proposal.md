## Why

A review round still starts with the user opening one session per reviewer and pasting the prompt into each. Over 30 days of this workflow, about 200 of 288 sessions existed only to run a pasted review prompt. `--run` does not help: it hands the prompt to a subagent of the author's own harness, which is the same model family. Every reviewer's tool already ships a command-line program that runs without a session window, so the author's session can start the reviewers itself.

## What changes

- `--run` takes the round's reviewers: `--run codex,pi`. A reviewer is `claude`, `codex`, `pi` or `vibe` (that tool's program, run headless), `glm` (Codex on the user's own Codex profile `zai`, for Z.AI's GLM models, so Codex can review on GPT and on GLM in one round) or `subagent`. A program's entry may name a model, everything after its first colon (`pi:glm-5.3`), so one program can review twice with different models; a model is ASCII letters, digits and `.`, `_`, `/`, `:`, `-` only.
- `--run subagent` is today's `--run`, now named: a fresh subagent that names its own result file. It stands alone and takes no model, and none of the program mechanics below apply to it.
- On `/braid:xreview`, the word after `--run` is still the scope when it is `diff`, `all` or an existing path, so `--run all` keeps working, and the list and the scope may come in either order (`--run codex,pi all`, `--run all codex,pi`). A word starting with `--` is a flag, never the list. On `next`, which has no scope, the word after `--run` is always the list.
- Without a list, `--run` reads a `Reviewers:` line from the Workflow section of the project's AGENTS.md, ignoring the spaces around its entries. With neither, it names the programs it finds installed, asks which to use, and offers to save the answer as that line (adding the section when missing; with no AGENTS.md it points to `/braid:standards` instead; with none installed it says so and names `--run subagent`). It never picks reviewers on its own; an entry it can't run, in the list or the line, stops the fan-out before anything starts.
- A script beside the skill, `run.cjs`, starts the round's programs at once in the working tree, tells each to read the prompt and do what it says and the exact result path to write (`r<N>-<program>.md`, or `r<N>-<program>-<model>.md` when the entry names a model, `-2` on a clash), stops any still running after 60 minutes together with its process tree, and prints a line per program as it finishes. A failed or stopped one is reported and the round goes on with the result files present; with none at all, the round stays ready and nothing changes.
- A result file without its closing `Verdict:` line is not a report yet, for a fan-out and for `next` alike: it is named as incomplete, not handled, and read by a later `next` once it is finished.
- Both paths go to a program relative to the working tree, and a review folder's name only ever holds ASCII letters, digits, `.`, `_` and `-`: xreview maps a path scope's other characters to `-` when it names the folder, and a hand-made folder with other characters is not fanned out. Nothing a shell could read as more than a name reaches a program's command line.
- While a fan-out runs, the review folder holds a marker of it. The fan-out counts as running while the process that started the programs or any of the programs is alive, and that process stops every program's tree when it is told to stop. `next` and a second fan-out on that review say the fan-out is still running, and name the marker file, instead of handling a half-finished round or starting a second set of programs; a marker whose fan-out is gone counts as none.
- Started programs run without approval prompts, each in its automatic approval mode where it has one (Claude Code's auto mode, Codex's approve-for-me, Vibe's smart-approve; Pi has none), with the user's rights except for Codex, which keeps its workspace sandbox, so they can run tests and write their file; they may load the project's own agent configuration (hooks, extensions, MCP servers) without asking. xreview says so before every fan-out.
- The prompt gains a cleanup rule for every reviewer, hand-started ones included: before finishing, remove whatever else it created (temporary files and folders, containers, images and volumes, background processes, branches, stashes and worktrees) and list what it could not remove. After a fan-out, the script names what differs from before the programs started: the review folder's own files, ignored or not (a changed prompt, a result file no entry was assigned), and in the repository files (apart from the assigned result files, the marker and ignored files), the index, the checked-out commit or branch, refs and stashes, worktrees, and the repository's hooks, local git config and local exclude file. It undoes nothing, and says it is a check on leftovers and not a guarantee: containers, processes that left a program's tree, ignored files and anything outside the repository are not covered.
- When the programs finish, the author handles the round as `next` does, without the user asking, so under `--run` one round follows another until the review closes or a question stops it. A session that can't keep waiting says they are still running and gives the full command to take the round up: `next` with the review's folder, `--run` with the reviewers, and `--auto` when it was given.
- `next --run` on a round with no result files (a mistyped reviewer started nothing, or every program failed) starts the reviewers on that round, so a failed fan-out can be started again without losing the review's rounds.
- The prompt tells a reviewer to use the exact result path its hand-off gives when it gives one, and to name its own file otherwise.
- The question after CONFIRMED findings (another round?) now comes with the author's recommendation and a one-line reason. A new `--auto`, accepted wherever `--run` is, waives that one question and nothing else. Under `--run`, past five rounds that question is asked before every further round, `--auto` or not.
- On an exposure hit before a fan-out to programs, on the first run or on `next`, the question also says the programs would run that code without approval prompts, and offers starting nothing beside online and offline; it is asked even when the prompt is already `--offline`. Going offline still gives every program the `--offline` prompt, with the warning that they are not held to it. A subagent hand-off behaves as today.
- Whenever a round is left for the user to hand on (no `--run`, or a fan-out that started nothing), xreview gives, with the prompt's path, the one line to paste to a reviewer: `Read <prompt path> and do what it says.`

## Impact

- Spec: `reports` (one requirement added, three modified; the third, on untrusted sources, only so its `--run` scenarios name `subagent` and point to the new question).
- Code: `skills/xreview/run.cjs` (new), `skills/xreview/run.md` (new), `skills/xreview/sources.md` (new), `SKILL.md`, `next.md`, `exposure.md`; a runner test in `scripts/check.cjs`; `biome.json` (its includes gain `skills/xreview/*.cjs`).
- Docs: ADR 0017, `braid/GLOSSARY.md`, `skills/help/SKILL.md`, README, `braid/map.md`, the optional `Reviewers:` line in `skills/standards/template.md`.
- Release: 1.9.0, a minor: the three `plugin.json` files and the CHANGELOG entry.
- Behavior that changes for today's users: `--run` with no reviewers named and no `Reviewers:` line now asks once instead of using a subagent; `--run subagent` is the old behavior. `--run diff`, `--run all`, `--run <existing path>` and `--run` followed by another flag keep their meaning. With or without `--run`, a path scope holding characters other than ASCII letters, digits, `.`, `_` and `-` now gets a review folder with `-` in their place (1.8.0 replaced only `/` and `\`); existing folders are untouched.
- Always-on budget: unchanged. xreview is user-only, so its description is not injected.

## Out of scope

- Handing implementation to another agent the same way: a later change, once the runner has proven itself on reviews, which only write one file.
- Worktrees for reviewers: the default scope includes uncommitted changes, which a fresh worktree does not hold, so it needs its own rules for carrying work in. Reviewers share the working tree, as they do today when started by hand.
- Enforcing `--offline`: Codex's sandbox is set with a flag. Claude Code's can be turned on per run through `--settings`, on macOS, Linux and WSL2 but not native Windows; Pi and Vibe have none. So `--offline` stays an instruction; enforcing it where a sandbox exists is a later option.
- Mixing `subagent` with programs: a subagent has no shared start, limit or finish signal with the runner, and a cold same-family review is already available by naming that harness's own program.
- Recovering a report from a program's output when it left no result file: started programs can write by construction, so a missing file is reported as a failure.
- A comparison that holds against a reviewer acting in bad faith: a program with the user's rights can act outside the repository, where no git comparison looks. The prompt's rules and the exposure question are the guard; the comparison finds leftovers.
- ZCode as a headless reviewer: no supported headless path for Coding Plan accounts today; GLM models are reached through Pi. A ZCode session can still be the author.
- Vibe as a harness: a separate change. Here it is only a program that reads a prompt.
- Arbitrary reviewer commands, a cost budget, and a time-limit flag: no one has asked; the four programs are a table in the script, and the limit reads one environment variable that the test needs anyway.
- Any dependency on a session manager (Pane or similar): the runner is a plain process every harness's shell can start.
