## Online by default, `--offline` to opt out

Weighed: always on with no flag, opt-in `--docs`, or on by default with `--offline`. The check is already conditional (only candidates that depend on external behavior), so it costs nothing on a diff without them, and opt-in would leave it off for the reviewers who most need it. `--offline` exists for air-gapped reviewers and for code that shouldn't meet the network: a reviewer with fetch holds all three legs of the "lethal trifecta" (private data, untrusted content, a way out), and the documented attack gets the agent to fetch a URL carrying private data. `--offline` means every way to the network, not just "web search" (Atlassian Rovo's injection survived disabling search because fetch stayed open), the shell included. It is still an instruction an injected reviewer could ignore; the hard control is starting the reviewer with network tools off in its harness, so xreview's suggestion names both.

## Doc-backed findings stay PLAUSIBLE

Weighed: PLAUSIBLE with a citation, CONFIRMED when the official docs for the pinned version say so, or a third DOCUMENTED label. CONFIRMED keeps meaning reproduced; docs can be wrong or describe an unreleased version. The URL and version in the evidence make the finding checkable without a new label.

## Injection wording names the signs

OWASP's cheat sheet notes that labelling external content "as data" doesn't enforce the boundary and that its own example prompts don't confer resistance. So the Sources section is specific rather than a bare "ignore instructions": what counts as untrusted (the diff and repo too, since an outside PR is the likeliest carrier), the signs (addresses the AI or reviewer, claims authority, grants permission, says to skip, approve or hurry, hides in comments, invisible markup or encodings), the action (report it quoted with its source, as a finding), and the exfiltration and execution limits (public query terms only, same-site pages only, nothing run because a page said to). Two exceptions keep it usable: the prompt and the files it names as the standard are judged against, not reported, and an instruction shown as an example (security docs, fixtures, agent instruction files, docs' command samples) is evidence, not an attempt. Neither covers text aimed at the review itself (skip, approve, what to report) that the scope adds or changes: on someone else's branch, the named proposal or AGENTS.md is written by the person under review. Review rules already on the base in agent instruction files or named rule files (Codex reads standing review rules from AGENTS.md) and the prompt's own Don't flag and Output rules are judged against, so for rules the line falls at what the scope changes; the same text elsewhere on the base, such as a code comment, is reported. A blanket verdict (approve the change, skip the review, report nothing) is the exception, reported wherever it sits, the base included, since a cloned repo's base is someone else's too. Weighed and declined: trusting base rules only when the local git user wrote them, which would also close a hostile base rule that subtly narrows the review, but would report a teammate's legitimate review rules as injections on every team repo. That narrowing case is the residual risk.

Guidance on the base for a project's human PR reviewers ("Reviewers: check the changelog" in CONTRIBUTING.md) is read as not aimed at this review, unless it approves, skips the review or says to report nothing. It addresses a reviewer, so the stricter reading would report it on every repo that has a contributing guide. Such guidance that the scope adds or changes is still aimed at this review, so a branch can't narrow the review through it; the reading gives up only the base narrowing case already accepted above.

The real boundary stays the reviewer's harness permissions; xreview points to `--offline` and a network-off reviewer when the code is someone else's or secrets sit in the working tree, and asks first under `--run`, where a suggestion after the hand-off would come too late. Secret-named files are skipped inside dependency, virtualenv and build-output folders by kind, not by ignore state: git commands disagree on whether a file is "inside an ignored folder", and a `secrets/` entry in `.gitignore` would hide the very file the suggestion exists for.

Not every wording edge case gets a rule: reviewers could already search before this change, which only makes the check routine and its limits explicit.
